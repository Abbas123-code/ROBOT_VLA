02 · Read this before running anything

Do not rerun the complete sequence on the robot's current state.The last confirmed live state is already holding the cube above the table. Approach/descent scripts expect open fingers and earlier arm poses. A reset also does not restore the measured scene automatically.
  • Simulation only. These scripts are not certified safety controllers and are not for a physical Panda.
  • No GPU changes: do not modify drivers, system CUDA, GPU settings, or reboot as part of this guide.
  • One motion source at a time. Keep enable_motion=false. Do not overlap a ROS approach publisher, the demo, and Script Editor motion tasks.
  • Check Play/Pause/Stop. Play advances physics. Pause freezes the current simulation. Stop may reset dynamic state and simulation time. Do not use Stop as a harmless pause.
  • A test is not the GUI. Isolated tests open another simulation and do not move the robot you see in your original window.
  • Never bypass a failed preflight by increasing tolerances or disabling checks. Diagnose the state mismatch.
  • No automatic release while lifted. Opening the fingers can drop the cube. A placement/release procedure has not been validated.
  • A successful script ends its monitoring. Drive targets remain, but long-term holding is not continuously supervised afterward.

Useful terminal basics

  • pwd shows your current folder; cd changes it. All relative commands here assume the project root, not its parent or ros2_ws.
  • source adds an environment to the current shell. It is not an installation.
  • Ctrl+C stops the foreground terminal program. It is not guaranteed to stop the simulated robot: a drive may retain its last target.
  • --once reads one ROS message and exits. timeout 10 bounds a waiting inspection command; a timeout is not a successful reading.
  • You may activate the Isaac venv with source env_isaacsim/bin/activate, but explicit interpreter paths below reduce environment confusion.

07 · Continue this session or restart from scratch?

Continuing the existing GUI

  • Do not rebuild, reopen or stop the scene unnecessarily.
  • Read fresh feedback and inspect the current cube pose.
  • Choose only the next stage whose starting conditions match.
  • Last confirmed state: initial 2 cm lift completed. Higher-lift execution is not confirmed in this record.

Fresh scene / reset / new machine

  • The robot is near HOME with a different base position.
  • Gripper session-layer drive settings may be absent.
  • The cube returns to the baseline and settles.
  • The historical approach start vector is not automatically restored.
The existing plans are specific to a measured state, not a general replay system.The GUI base was measured at approximately [-0.0991988853, -0.0000007233, 0.0000269338] m with quaternion [1,0,0,0]. The saved scene uses a near-zero base position. The initial approach was planned from [0.1207,-0.7821,0.0002,-2.3576,0,1.5707,0.7854] rad. A new scene normally does not match both of these conditions.

Safe procedure after a reset

  1. Start with observation only; keep demo motion off.
  2. Run the live pose inspector and read joint feedback.
  3. Compare base position/orientation, cube pose, finger state and arm start against the desired plan.
  4. If anything differs, stop. Recompute IK/trajectory from the actual state and test it in isolation. The current scripts do not automatically solve a new plan.
  5. Only execute when start, geometry and validation match. Do not teleport the live arm to bypass a guard.

Important limitation: the ROS approach preflight checks joint start, finger state, graph, clock, demo status, and hashes of the plan and saved scene. It does not receive the live cube/base pose. A passing preflight cannot detect every unsaved GUI scene edit. The operator must check the live geometry.

The lift scripts also contain fixed validated joint targets and specific starting-height checks. Repeatedly pressing Run is not an “up another 5 cm” command.

What the ROS controller checks

  • Domain 42, passing plan and saved-scene hashes, finite/limited arm angles.
  • Initial arm pose within 0.015 rad of the plan; open fingers within 0.002 m.
  • Fresh feedback and clock, stable graph discovery, one simulator and no unexpected command publishers.

10 · Close and hold the gripper

Isaac Script Editor Use isaac/scripts/close_panda_gripper.py. This is not an ordinary terminal Python program.

Why this needed a GUI-side script

The saved imported finger drives had stiffness 0, damping 0 and a 20 N maximum force. A ROS position command alone would not provide the intended holding drive. The closure script configures the existing drives in the session layer, without changing GPU settings or attaching the cube.

SettingValueInterpretation
Drive typeforcePosition-error-based motor drive with force limit.
Stiffness / damping1000 / 20Drive gains used in the tested scene.
Max force5 N per fingerA limit, not a measured constant contact force.
Open position0.04 m per fingerAbout 8 cm total nominal opening.
Commanded closed target0.023 m per fingerThe cube stops actual travel near 0.02508 m; this difference produces squeeze.
Timing4 s closing + 2 s observationNo arm lift during closure.

Run it

  1. Finish the cube-entry move. The fingers must be open and beside the cube, not above it.
  2. Keep the demo off and stop other motion publishers. Leave Isaac playing.
  3. Copy the entire closure file into Isaac's Script Editor, replacing the previous code.
  4. Click Run once. The script schedules an asynchronous task; wait for its output.
  5. Success prints "closed_and_holding": true. Check the fingers visually and keep the output or a screenshot.

It checks live gripper alignment, both finger contacts, finger symmetry, arm stability, cube motion and tilt. It uses FOUND/PERSIST/LOST contact lifetimes because sleeping bodies stop emitting repeated contact events. On a handled failure while playing, it requests measured finger-position targets to remove squeeze; it does not deliberately reopen or move the arm.

Do not rerun closure on already-closed fingers.The initial open-finger check will reject it. Do not remove that check. “Holding” means drive-based contact, not a fixed constraint and not yet proof of successful lifting.

11.2 Additional lift: 5 cm

Prepared and isolated-tested; live outcome pending

  1. Begin only from the successful initial 2 cm lift. The cube centre should be near world Z = 0.045 m.
  2. Open isaac/scripts/lift_panda_cube_higher.py in VS Code.
  3. Copy its complete, short contents into Isaac's Script Editor, replacing the previous script.
  4. Click Run once. It loads the updated main controller from the local project, then requests higher=True.
  5. Wait for 10 seconds of motion and 2 seconds of holding.
  6. Expect lift_verified: true and lift_profile: additional_5cm. Save/share this output to confirm the live result.

The isolated test ended with the cube centre at Z ≈ 0.0946 m. For an upright 5 cm cube, its bottom is then about 0.0696 m above the table—not 9.46 cm. This is a test result, not the current GUI height.

What both lift modes protect against

  • Wrong initial arm pose, wrong cube height or alignment, incorrect base pose, missing contact reporters, or changed gripper gains.
  • Joint tracking error above 0.02 rad; finger positions changing by more than 0.0015 m from the initial grip.
  • Cube/gripper relative displacement above 3 mm; cube XY drift above 4 mm; tilt beyond the configured limit.
  • Unexpected reported robot contacts and clock/stage/playback changes.
  • Failure to achieve the requested cube rise within ±4 mm.

On a motion failure, the script pauses physics. It does not open the gripper, keep moving upward, or automatically lower the cube. Read the error before resuming. Reporters are reused from closure; the contact check is not an exhaustive self-collision monitor.

Why run this inside Isaac instead of sending blind ROS arm commands?The GUI-side controller can check the cube's actual world pose every update. ROS joint feedback alone cannot tell whether the cube followed the hand or fell. This assistant cannot directly click Run in your desktop Isaac Script Editor, so that is the manual execution step.

The higher-lift entry currently contains this machine's absolute project path. If the project is moved, update that path and revalidate before use. Do not rerun either lift from an already higher pose or edit constants to request an arbitrary lift.

15 · Stop, pause, reset and preserve work

If something looks wrong while moving

  1. Click Pause in Isaac Sim to freeze physics. This is a simulation action, not a hardware emergency stop.
  2. Do not reopen the gripper or enable the demo while diagnosing.
  3. Read the Script Editor or terminal error. Record the message and current stage.
  4. Stop a running terminal controller with Ctrl+C if needed. Do not assume this alone cancels retained drive targets.
  5. Keep the demo parameter false. Before pressing Play again, inspect pending targets and resolve the failed guard. A paused script may have left a previously commanded target active.

What persists?

  • GUI closure/lift author changes into the USD session layer. They leave drive targets active but do not save the stage.
  • An ordinary save of the root layer is not a complete runtime checkpoint. It does not automatically capture the session layer, dynamic pose, controller state or grasp history.
  • Pause usually preserves the current simulated state. Stop/restart, stage reopen or app exit must be treated as state invalidation; verify again.
  • Approach commands are runtime actuator targets. Report JSON and screenshots are evidence, not restartable simulator snapshots.

What to back up

Preserve source scripts, configs, this guide, the original asset revision/licenses and screenshots. For reproducibility also archive the generated scene with all referenced generated assets, environment/package information and relevant reports. Many of these are ignored by Git.

Starting over intentionally

Only do this when abandoning the current held-object state is acceptable. Pause, stop motion sources, then close/reopen or rebuild the baseline as needed. Return to section 07: fresh poses require replanning. There is no tested one-button safe placement/reset routine yet.

17 · Small details that matter

Coordinates and units

  • World: the scene's fixed coordinate system. Z points up; gravity is −9.81 m/s² along Z.
  • Base: panda_link0 coordinates. World position = base translation + base rotation × base-relative position.
  • Grasp target: panda_grasptarget is 0.105 m along the hand's local Z. With the hand pointing down, it lies below the hand origin. It is a coordinate frame, not a measured finger-tip clearance.
  • Quaternion ordering: these scripts use w,x,y,z, not x,y,z,w.
  • ROS arm positions: radians. USD angular drive targets: degrees. Finger prismatic joints: metres. Mixing these can produce very wrong motion.
  • Cube: 0.05 m side length, 0.05 kg mass. Centre on table ≈0.025 m; top≈0.05 m. Baseline saved centre starts at0.04 m and settles.
  • Cube height vs clearance: upright cube bottom = centre Z −0.025 m. The grasp-frame height is not the cube-bottom height.

FK, IK and the paths we used

FK (forward kinematics) computes hand pose from joint angles and URDF transforms. IK (inverse kinematics) solves joint angles for a desired pose. Offline SciPy least-squares calculations produced the tested targets; there is no standalone automatic replanner in this project yet. The redundant arm solve held joint3 fixed for these poses and used joint bounds.

Motion uses smoothstep interpolation: s = clamp(t / duration, 0, 1), b = s²(3 − 2s), q = q_start + b(q_target − q_start). This gives zero nominal endpoint velocity. It is a joint-space path, not a guaranteed perfectly straight Cartesian line.

What “lock the gripper” means here

The motor targets keep applying bounded squeeze against the cube. There is no weld, parenting trick, kinematic attachment, or artificial fixed joint. The demonstrated lift therefore depends on physics contacts and friction. A 5 N maximum drive setting is not proof that each contact continuously measures exactly 5 N.

Scene construction details

  • Panda is imported with a fixed base. Original scene self-collisions are disabled; the approach isolation test enables checks and excludes rigidly fixed assembly pairs whose imported meshes overlap.
  • Table translation: (0.35,0,−0.625) m. Its joints are deactivated and rigid-body/articulation APIs removed so it is static scenery.
  • Arm drives: stiffness400 and damping40 for all seven joints; max effort87 for joints1–4 and12 for joints5–7. Those 12 values are effort limits, not stiffness values.
  • Floor: centre (0,0,−0.68) m, size6×6×0.1 m. Overview camera looks from (2,2,1.6) toward (0.3,0,0.2).
  • The importer preserves originals; generated URDFs contain absolute mesh paths and use the cleaned link6 STL. This can change visual fidelity for that link.

What the tests do not prove

A passed finite simulation is not a guarantee for all poses, objects, friction values, loads or future edits. The current system has no physical robot safety layer, no long-term grip watchdog after scripts finish, no general obstacle planner and no vision-based pose estimator. Keep the experiment scope explicit.
